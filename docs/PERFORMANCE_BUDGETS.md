# Captail Recording & Replay Performance Budgets

Цей документ фіксує бюджети продуктивності, методологію тестування та емпіричні результати бенчмарків після реалізації плану оптимізації процесу запису Captail.

| **Record: Record-to-first-byte (Warm)**        | < 250 ms                     | **45.0 ms**                          | **PASS** |
| **Record: Stop-to-file-ready**                 | < 2000 ms                    | **60.2 – 61.2 ms**                   | **PASS** |
| **Replay-Record: Lagged frames %**             | < 0.10%                      | **0.000%** (0 / 300 кадрів)          | **PASS** |
| **Advanced Audio (10 процесів): CPU Overhead** | < 1.0% додаткового CPU       | **~0.6%** (31 ms CPU / 5000 ms real) | **PASS** |

## 3. Впроваджені архітектурні оптимізації

### 3.1. NVENC Low Overhead за замовчуванням

- Новий типовий режим кодування для нових конфігурацій: `low-overhead`.
- Параметри кодувальника:
  - Preset: `p2` (fastest NVENC preset with minimal GPU compute overhead);
  - Tune: `ll` (ultra-low latency);
  - Multipass: `disabled` (економія GPU memory bandwidth);
  - Lookahead: `false` (усунення додаткових затримок і буферів кадрів);
  - B-frames: `0` (зниження jitter та затримок);
  - Адаптивне квантування (AQ): окрема керована опція в налаштуваннях.
- Повна зворотна сумісність: існуючі конфігурації з явним `balanced` зберігаються без змін; відсутній тег мігрує в `low-overhead`.

### 3.2. Опціональне призупинення Instant Replay під час ручного запису (`SuspendReplayDuringRecording`)

- За замовчуванням: `true`.
- При старті ручного запису:
  1. Створюється та стартує `_recordingOutput`, що підключається до вже існуючих спільних кодувальників (відео та аудіо).
  2. Лише після активного запуску ручного запису `_output` (replay buffer) призупиняється через `obs_output_stop`.
  3. `OnOutputStopped` пригнічує перехід у стан аварії (`Faulted`), позначаючи стан як `_replaySuspendedForManualRecording`.
  4. Індикатор запису відображає спеціальний стан `Suspended` (акуратне пунктирне кільце сірого кольору).
  5. `AvailableReplaySeconds` повертає `0`, збереження буфера блокується з коректним повідомленням користувачу.
  6. При завершенні ручного запису буфер Instant Replay відновлюється з нуля, не навантажуючи дискову підсистему та пам'ять паралельним дублюванням.

### 3.3. Теплий конвеєр запису (`KeepRecordingPipelineWarm`)

- За замовчуванням: `false` (з можливістю активації в Налаштуваннях).
- Для користувачів, які не використовують Instant Replay, але прагнуть мінімальної затримки старту ручного запису:
  - Ініціалізує libobs, джерела відео/аудіо та кодувальники у фоні;
  - Жоден вивід не пише на диск і не заповнює RAM;
  - Знижує затримку старту запису з ~600–1200 ms (cold start з ініціалізацією OBS) до **45 ms** (warm start).

### 3.4. Діагностика фіналізації та навантаження диска

- У `ObsReplayEngine.StopRecordingAsync` додано високоточний вимір тривалості фіналізації файлу (`Stopwatch`).
- Якщо фіналізація перевищує поріг 2000 ms, у лог записується попередження для виявлення дискового backpressure.
- Збережено налаштування муксера `frag_keyframe+empty_moov+delay_moov` для максимальної стійкості до збоїв.

---

## 4. Рекомендації для подальшого розвитку

1. **Динамічний вибір Warm Pipeline**: увімкнення `KeepRecordingPipelineWarm = true` за замовчуванням на системах з ≥ 16 GB RAM та дискретними GPU.
2. **Аудіо-буферизація процесів**: поточний опитувальний інтервал (1000 ms / 250 ms при сплесках) демонструє стабільні 0.6% CPU overhead при 10 активних процесах, що є повністю безпечним для 1% lows.
